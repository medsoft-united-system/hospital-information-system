### 3.2. Каналы и безопасность

1. **HTTPS** использует существующую серверную TLS-проверку, без обязательного клиентского сертификата. `POST /api/service-auth/token` принимает `{ "apiKey": "..." }`, `POST /api/service-auth/refresh` — `{ "refreshToken": "..." }`. Ответ сохраняет текущие поля `accessToken`, `accessTokenExpiresAt`, `refreshToken`, `refreshTokenExpiresAt`. Не менять wire-формат LIS.
2. Wire-роль нового аккаунта — `HL7Import`, название в UI — **HL7 Import**. Импортёр не получает FHIR-доступ, доступ к обычным CRUD API, аудиту или управлению аккаунтами. Получение/обновление токенов и тест подключения разрешены.
3. `GET /api/testConnection` доступен **всем аутентифицированным ролям**, а не анонимно. Новая роль должна получать `200` и фактическое `role=HL7Import`; LIS продолжает получать `LIS`. Для существующих человеческих ролей endpoint принимает их текущую схему аутентификации и возвращает честную human identity/роль без фиктивного serviceAccountId. Для HL7Import не заявлять FHIR-права: дополнительные возможности probe показывать отдельно, сохраняя прежний ответ LIS и совместимость его клиента. Проверить обе схемы отдельной матрицей, не ослабляя FHIR policies.
4. **MLLP** — отдельный TCP-порт, поверх TLS с обязательным клиентским сертификатом. Предлагаемый dev-порт — `2575`, настраиваемый. Клиент проверяет CA, срок и SAN/hostname сервера; HIS проверяет доверенную цепочку, срок и Client Authentication EKU клиента. Не отключать validation.
5. Клиентский сертификат содержит имя сервисного аккаунта в Subject CN для справки. **CN не является логином, не определяет роль и не сравнивается с именем аккаунта при авторизации.** Сертификат и JWT проверяются независимо. Доверенного сертификата без JWT недостаточно, как и JWT без сертификата.
6. Access JWT передаётся **в UAC каждого сообщения**, включая MLLP probe. Перед обработкой проверяются подпись/алгоритм/issuer/audience/время, тип сервисной identity, текущая сессия, активность аккаунта/версия и `HL7Import`. Состояние повторно проверяется для следующего сообщения: открытое TLS-соединение не продлевает права.
7. API key, access/refresh и private key не выводятся в UI-диагностику, журнал, ACK, fixtures и git. Журнал может показывать `UAC: [скрыто]`, тип сообщения, control ID, время, ACK-код и отпечаток сертификата.

### 3.3. MLLP framing и жизненный цикл

- Кадр: `0x0B` + HL7 payload UTF-8 без BOM + `0x1C 0x0D`. Сегменты заканчиваются `\r`, а не `\n`.
- По одному пациенту в одном ADT; один ACK после commit/rollback этого пациента. Транзакции на весь XML нет.
- Для первой версии достаточно **одного сообщения и ответа на одно mTLS-соединение**. Не требовать pooling или pipeline. Сервер всё равно обязан читать TCP как поток: один `Read` не равен одному кадру.
- Предлагаемые лимиты профиля: 1 MiB на payload, не более 100 DG1, TLS handshake 10 секунд, чтение кадра 30 секунд, обработка/ожидание ACK 30 секунд. Лимиты настраиваются, одинаковые значения проверяются в fixtures/тестах; это инженерные ограничения, не цитата из задания.
- Отсутствующий start/end marker, неполный кадр, NUL, превышение лимита и неизвестная версия обрабатываются предсказуемо. Если нельзя надёжно извлечь MSH-10, закрыть соединение с безопасной диагностикой, не выдумывая ACK чужого сообщения.
- Нет автоматической повторной отправки ADT после обрыва/timeout: результат может быть уже сохранён. UI показывает **«Исход неизвестен»**. Пользователь может повторить импорт явно; уникальность внешнего ID защищает от дубля, ответ будет дубликатом, а не новым успехом.

### 3.4. Сообщение пациента

Профиль использует `MSH → UAC → EVN → PID → PV1 → DG1*`. Обязательные EVN/PV1 не выбрасываются при отсутствии визита. Это **ограниченный учебный профиль**, а не реализация всех структур HL7. Базовый тип — `ADT^A28^ADT_A05`, версия `2.8`. Повтор DG1 используется по условию и допускается структурой ADT_A05; результат в MSA-3 — отдельная лабораторная legacy-оговорка.

| Поле | Договорённость |
|---|---|
| MSH-1/2 | `\|` и `^~\&`; специальные символы данных экранировать стандартными HL7 escape-последовательностями |
| MSH-3/4 | `MEDSOFT_IMPORT` / `LAB4_XML`: стабильный источник, не имя оператора или текущего аккаунта |
| MSH-5/6 | `HIS` / `MEDSOFT` |
| MSH-7 | Время с timezone; UTC в примерах: `20261113120000+0000` |
| MSH-9 | `ADT^A28^ADT_A05` |
| MSH-10 | Новый уникальный message control ID на отправку; это не внешний ID пациента |
| MSH-11/12 | `P` / `2.8` |
| MSH-15/16 | Оригинальный режим ACK: оба пустые, один прикладной ACK после транзакции |
| MSH-18 | `UNICODE UTF-8` |
| UAC | Креденшел JWT в ED: `UAC-1=JWT^JSON Web Token^99MEDSOFT`, `UAC-2=MedSoftDesktop^application^jwt^Base64^<base64>`; `<base64>` — Base64 от UTF-8 исходного access JWT без переноса строк и префикса `Bearer `. `JWT` — локальный credential type, `application/jwt` — MIME; Base64 не является шифрованием |
| EVN-2 | Время записи события; для нового импорта равно времени формирования MSH-7. Иное клиническое время из XML передаётся отдельно после mapping |
| PV1-2 | `N` (Not Applicable), если визита нет: минимальный сегмент `PV1\|\|N` |
| PID-3 | CX: внешний ID пациента в CX.1, assigning authority `LAB4_XML` в CX.4, тип `PI` в CX.5 |
| PID-5 | XPN: фамилия / имя / отчество в согласованных компонентах; кириллица UTF-8 |
| PID-7 | Дата рождения `YYYYMMDD`; не превращать дату без времени в timestamp |
| PID-8 | Из XML кириллические `М → M`, `Ж → F`, затем mapping в AdministrativeSex HIS. Для неопределённого значения профиль допускает `U` |
| DG1-1 | Порядковый номер `1..N` |
| DG1-3 | CWE `icdCode^icdTitle^I10`, где `I10` в третьем компоненте обозначает систему ICD-10 из HL7 table 0396. Неизвестный код добавляется в реестр |
| DG1-5 | Обязательное `diagnosed_at` данного XML в формате `yyyyMMddHHmmss±HHmm`, timezone берётся из явного SourceTimeZone профиля |
| DG1-6 | `U^Unspecified^99MEDSOFT`, локальное значение user-defined diagnosis type. XML содержит время диагноза, клинический статус в нём отсутствует |

В DG1-3 передаются CWE-компоненты `code^name^codingSystem`. `I10` в coding system и код самого диагноза `I10` имеют разные позиции и смысл. Коды `I10`, `I48`, `J45.9` сохраняются точно после существующего trim. Старые шестисимвольные коды HIS поддерживаются наряду с новыми.

Время XML интерпретируется через явную настройку **SourceTimeZone**, согласованное значение по умолчанию — **Europe/Moscow**. Это выбранная договорённость профиля, поскольку в файле timezone отсутствует. Настройка видна в desktop до импорта и фиксируется в данных запуска. Эта договорённость принята вместе с C4 16.11.2026. Системная timezone машины пользователя на mapping не влияет.

Для записи `2023-05-14T10:20:00` при профиле Europe/Moscow клиент формирует DG1-5 `20230514102000+0300`. HIS сохраняет клинический момент `2023-05-14T07:20:00Z` и переданный offset интерпретации `+180` минут либо эквивалентное представление, позволяющее восстановить `10:20:00`. При неоднозначной/несуществующей дате выбранной зоны требуется явная ошибка валидации.

`AddedAtUtc` и `OccurredAtUtc` истории формируются временем импорта на HIS. `DiagnosedAt` хранит отдельную клиническую дату 2021–2024 годов. Снимок ЭМК до создания карты не содержит импортированных записей, после импорта показывает сохранённую дату диагноза. В UI у этих двух дат отдельные подписи и секунды. XML не задаёт статус final/working, поэтому для обязательного DG1-6 профиль использует локальное `U`.

Каждое поле реального файла имеет место в таблице 3.1. L3/T3 проверяют round-trip значений через XML → HL7 → HIS и чтение карточки/ЭМК.

### 3.5. ACK, ошибки и probe

| Результат | MSA-1 | MSA-2 | MSA-3 по условию лабораторной |
|---|---|---|---|
| Пациент сохранён вместе со всеми диагнозами | `AA` | Исходный MSH-10 | Новый UUID пациента HIS |
| Внешний ID уже импортирован | `AE` | Исходный MSH-10 | `DUPLICATE: пациент уже импортирован` |
| Валидное сообщение, но клинические данные недопустимы | `AE` | Исходный MSH-10 | `VALIDATION: безопасное описание` |
| Нет прав/недействительный JWT | `AR` | Исходный MSH-10 | `AUTH: доступ запрещён` |
| Неподдерживаемый тип/версия/структура | `AR` | Исходный MSH-10 | `PROTOCOL: безопасное описание` |
| Ошибка БД/инфраструктуры с rollback | `AE` | Исходный MSH-10 | `INTERNAL: импорт не выполнен` |

`MSA-3` — требование именно этой лабораторной: поле устарело/выведено из стандарта до v2.8. Не выдавать такую передачу UUID за современное стандартное назначение MSA-3. Общие поля MSH/MSA и correlation заполняются по HL7; для UAC/auth-ошибок обязателен ERR с `ERR-3=207`, severity Error и безопасной диагностикой в ERR-7; для остальных ошибок ERR можно добавить по профилю. Клиент отображает согласованные MSA-поля, не раскрывая подробности проверки JWT. Текст ошибки HL7-экранируется, не содержит SQL, exception stack, JWT или содержимого ключа.

У ACK собственный MSH-10, отправитель/получатель меняются местами, MSH-12 `2.8`. Для A28 ответ `ACK^A28^ACK`; при отказе неподдерживаемому сообщению с читаемым trigger event ACK-9.2 копирует исходный MSH-9.2. **AA импорта отправляется только после commit.** Если ACK потерялся после commit, это неизвестный исход клиента, а не причина откатывать уже подтверждённую БД транзакцию.

Для **проверки MLLP** используется `NMD^N02^NMD_N02` с `MSH`, `UAC`, `NCK`; `NCK-1` содержит текущее время с timezone. Ответ — `ACK^N02^ACK`, `MSA-1=AA`, `MSA-2=исходный MSH-10`, `MSA-3=CONNECTED`. Auth/protocol failure возвращает AR и безопасное описание. Это стандартное сообщение управления приложениями, используемое нашим профилем как connectivity probe, а не универсальная HL7-команда ping. Время NCK информационное: **не устанавливать системные часы**. Проверяются mTLS, framing и UAC; импорт и запись пациента не вызываются. Проверка TCP-порта и HTTP `/api/testConnection` этот тест не заменяют.

### 3.6. Идентификаторы, сохранение и авторство

1. HIS создаёт собственный UUID пациента. Внешний ID сохраняется отдельно с источником; для C4 источник фиксирован `LAB4_XML`. Дубликат — та же пара `(sourceSystem, externalPatientId)`, независимо от сервисного аккаунта, сертификата, нового message ID и состояния пациента. Сейчас в HIS удаление пациента физическое и при наличии ЭМК запрещено; импорт создаёт ЭМК, поэтому проверить отказ удаления и сохранность external identity. Новую tombstone/soft-delete модель в этот план не включать без отдельного решения. Не искать дубль по ФИО/дате рождения.
2. Не удалять ведущие нули, не приводить внешний ID к UUID/числу и не менять регистр без основания в реальном XML. Пустой ID — ошибка. ID считается точной строкой с заданными ограничениями длины, нормализация ограничивается явно согласованной обработкой внешних пробелов.
3. Уникальный индекс БД обязателен: предварительного SELECT недостаточно при конкуренции. Два одинаковых одновременных импорта дают один commit и один `DUPLICATE`.
4. В одной транзакции: пациент, связь внешнего ID, ЭМК, диагнозы ЭМК, недостающие определения справочника, история и успешный аудит. Невалидный второй диагноз откатывает и пациента, и первый диагноз, и новые определения справочника.
5. Существующий диагноз определяется **по коду** с текущими правилами нормализации HIS, не по названию. Существующее название не перезаписывать. Каждое вхождение DG1 сохраняется в ЭМК, в том числе один код с разными клиническими датами. Определение в справочнике остаётся одним на код. Конфликтующие названия одного нового кода в одном сообщении требуют явной ошибки. Конкурентное добавление одного нового кода не должно ломать второй допустимый импорт.
6. Решение владельца проекта от 17.11.2026: сохранить уникальность кодов и названий. Новый код с названием, уже принадлежащим другому коду, отклоняет импорт всего пациента с validation; пациент, external identity, ЭМК, диагнозы, новые определения и успешный аудит откатываются. Не дописывать суффикс, не заменять код и не выдавать частичный успех. Такое ограничение может отклонить вход из другой версии справочника: автоматического сопоставления кодов по названию нет. Тест воспроизведения — `ExistingTitleWithDifferentCode_ShouldRejectEntirePatientAndKeepCatalogUnchanged`.
7. Источник клинического изменения — проверенный сервисный аккаунт. Сертификат — метаданные соединения. Не подставлять существующего медработника/администратора. Создание ЭМК и импорт диагнозов должны корректно отображаться в истории, списках, снимке на дату и API.
8. События отказа/дубликата пишутся отдельным безопасным способом после rollback, не сохраняя частичные медицинские данные. Ошибка аудита успешного импорта должна откатывать импорт.

## Прогресс L5 на 17.11.2026

Добавлен `Hl7MllpListener` — отдельный opt-in TCP listener в процессе API. По умолчанию `Hl7Import:Enabled=false`: старый HIS/LIS запуск не требует новых сертификатов. Hosted service стартует после миграций и инициализации, выполняемых Program до app.Run. При включении настройки и TLS-материал проверяются до bind; ошибка порта/сертификата не превращается в молча работающий небезопасный listener.

Каждое соединение использует TLS 1.3 с обязательным клиентским сертификатом, custom-root trust, Client Authentication EKU и проверкой срока. AIA downloads, renegotiation и TLS resumption отключены. Клиент отдельно проверяет CA и SAN сервера. CN клиента не выбирает сервисную identity. Метаданные ImportClientCertificate берутся из настоящего RemoteCertificate после успешного mTLS; JWT и текущая роль проверяются L2/L4 для каждого сообщения.

`MllpFraming` читает один кадр из произвольных порций TCP, проверяет 0B/payload/1C0D и размер до 1 MiB. NUL, вложенный start, неполный конец и coalesced trailing data отклоняются. Semaphore ограничивает активные соединения, лишние закрываются без очереди прикладных задач. Handshake, frame read, processing, write и shutdown имеют отдельные абсолютные deadlines. На сообщение создаётся DI scope; отмена processing передаётся EF и закрывает сокет, scope остаётся жив до завершения обработки. Stop отменяет/закрывает соединения и ограниченно ожидает задачи; TLS-материал освобождается после их завершения.

Итоговая проверка: 1651 unit-тест, 630 обычных интеграционных тестов и 24 сетевых TLS-теста; ошибок и пропусков нет. L5 добавляет 89 unit- и 24 сетевых сценария. Linux-профиль `python3 scripts/verify-lab4-transport.py` выполнил 24 реальных TLS/TCP-сценария с JWT и PostgreSQL без ошибок/пропусков: ADT, actual cert audit, probe, duplicate, отказы сертификатов/токенов, SAN, TLS 1.2, malformed frames, абсолютные deadlines, лимит, shutdown, автоматический выбор client cert и запуск через API-host. Обычные dotnet tests не включают отдельный профиль; он явно компилируется с `EnableMllpTlsTests=true`. Скрипт использует копию исходников без gitignored файлов и отдельную тестовую БД.

CRL/OCSP в текущем локальном CA-профиле не проверяются (`NoCheck`); доверенная цепочка/EKU/срок проверяются, отзыв JWT-сессий действует независимо. Production PKI с revocation infrastructure этим этапом не заявляется. Настройка/сборка стенда через Makefile относится к L7, отображение подробностей аудита — к L6.

Существующие значения `LIS` не перенумеровывать.
- Убрать предположение «все сервисы — LIS» из выдачи/refresh/identity и `/api/testConnection`, сохранив совместимость API, существующей audience `MedSoft.Lis` и Argon2id/ротации ключей. Если понадобится новая audience, предусмотреть явную совместимую миграцию, а не ломать токены работающей LIS.
- Вынести общую JWT/session validation для HTTPS и MLLP без зависимости от HttpContext и без самодельного декодирования JWT вместо проверки подписи.
- Policies: FHIR read/write только LIS; HL7 import только `HL7Import`; человеческие токены не дают MLLP import. `/api/testConnection` — общая проверка для всех аутентифицированных ролей по условию.

**Приёмка:** матрица LIS/HL7Import/админ/медроли/аноним; правильные token/refresh/probe; отказ чужим API; отзыв и refresh replay; просроченный/неправильно подписанный JWT. Проверить текущие LIS fixtures и integration tests без изменения ожидаемой роли LIS.

### L3. Атомарный импорт пациента, внешних ID и диагнозов — 8 SP

**Результат:** одна команда импортирует целого пациента либо не меняет медицинские данные.

- Добавить внешнюю identity и уникальный индекс с миграцией, не переписывая имеющихся пациентов и не сбрасывая рабочую БД.
- Реализовать transaction boundary для всех объектов из 3.6. Не вызывать цепочку существующих CRUD handlers с отдельными `SaveChanges` и не делать HTTP-запросы к собственному API.
- Сохранить coding system, исходное название и клиническое `DiagnosedAt` с offset из 3.4 в Domain/DBO/DTO, payload истории, snapshot replay и UI. Импортная дата остаётся в AddedAtUtc/OccurredAtUtc. Старые payload без DiagnosedAt продолжают читаться с пустым клиническим временем, их дата импорта сохраняется. IANA zone ID через DG1-5 не передаётся, сервер хранит offset из сообщения. Round-trip тест проверяет все 100 записей, включая точное исходное локальное время.
- Поддержать сервисное авторство создания ЭМК и диагнозов в Domain/DBO/истории/constraints/мапперах/снимках: сейчас требуются MedicalWorker и ограничен набор сервисных событий. Не фиктивный врач и не «просто nullable FK» без правил ровно одного автора.
- Расширить существующее правило кода с ровно 6 до 3–32 символов, названия с 3–24 до 3–256. Все 25 кодов файла имеют длину 3/5, 16 названий превышают 24 символа. Обновить Domain, FluentValidation, DTO, EF max lengths/CHECK, snapshots, UI maxlength/подсказки и UiMock. Сохранить существующие шестисимвольные и локальные коды, REST/CSV-пути и актуализировать проверки старых лимитов. Сопоставление остаётся точным по коду после trim, `I10` и `I10.00` — отдельные коды.
- Неизвестные коды добавлять в реестр; существующие не переименовывать. Учесть текущую уникальность названий и нормализацию кодов, конкуренцию и устойчивость внешней identity.
- Для повторного внешнего ID вернуть duplicate и не обновлять ни ФИО, ни дату рождения, ни диагнозы, даже если XML изменился.

**Приёмка:** PostgreSQL-тесты rollback на середине, два параллельных дубля, два пациента с одним новым кодом, отказ аудита, запрет удаления импортированного пациента с ЭМК, повтор через новый аккаунт; данные видны в карточке и ЭМК HIS с корректным автором. Unit-тестов без настоящей БД для атомарности недостаточно.

### L4. Декодер HL7 v2.8 и генератор ACK — 5 SP

**Результат:** HL7 payload преобразуется в вход импорта без потери полей; ответ соответствует C4.

- Разделить parsing, профильную валидацию, mapping и ACK builder. Применить проверенную HL7 v2 библиотеку с подтверждённой поддержкой нужных типов либо ограниченный явно протестированный codec; Firely FHIR SDK не является HL7 v2 parser.
- Проверять MSH-9/10/12/18, UAC, PID/CX/XPN, все DG1, escape-последовательности, кодировку и обязательность. Не разбирать клинические данные простым `Split('|')` без handling escape/components/repetitions.
- Реализовать mapping `М/Ж`, patronymicName, ICD-10 CWE и клинического времени из 3.1/3.4. Валидация разделяет birthDate, diagnosed_at и момент записи события импорта.
- AA/AE/AR, собственный ID ACK и correlation MSA-2; MSA-3 с UUID/безопасной ошибкой по лабораторному профилю.
- Отдельный маршрут probe не создаёт пациента.

**Приёмка:** fixtures обеих сторон; кириллица, `|^~\&`, несколько DG1, malformed input, ошибки UAC/версии и ACK correlation. Секретов в исключениях/ACK нет.

### L5. MLLP-сервер с mTLS и ограничениями — 8 SP

**Результат:** отдельный сетевой вход HIS безопасно вызывает L3 и возвращает ACK.

- Предлагаемое размещение: `Presentation/...Api/Hl7` для HostedService/transport adapters; настройки/регистрация отдельно. Для первого релиза listener может жить в процессе API, но не на HTTP endpoint. Domain/Application не зависят от SslStream/TcpListener.
- Конфиг `Hl7Import:Enabled/Port/ServerCertificate/ClientTrust/Timeouts/Limits`; секреты вне git. Выключенный listener не мешает обычному запуску HIS/LIS. Не включать обязательный client certificate на всём HTTPS API.
- На соединение использовать TLS с проверкой клиента, извлекать immutable cert metadata из реально проверенного peer certificate. На сообщение создавать DI scope, проверять UAC/роль и передавать transport context явно, не через статический current user. Текущий `HttpAuditActorAccessor` без HTTP возвращает System: добавить корректный message-scoped service actor, не теряя автора импорта. Listener принимает сообщения только после успешных миграций/инициализации.
- Реализовать framed reads, deadline, cancellation, лимит размера/параллельных соединений, отказ malformed input и graceful shutdown. Долгий клиент не блокирует остальные.
- Привязать ACK к результату transaction: успех после commit, исключения безопасно преобразуются, потеря ACK не запускает импорт повторно.

**Приёмка:** реальный локальный TLS/TCP: валидный client cert + JWT, без cert, чужой CA, expired cert, неверный EKU/SAN сервера, LIS JWT, отозванный JWT, обрыв и порционный ввод; probe и ADT; остановка процесса без зависших задач.

### L6. Аудит сертификата и отображение импорта в HIS — 3 SP

**Результат:** преподаватель видит, каким аккаунтом и с каким клиентским сертификатом выполнен импорт.

- В событии импорта хранить service account ID/name, message ID, source/external ID, число принятых диагнозов, итог и HIS patient ID при успехе. По макету показать фильтры «Импорт (HL7)»/период и раскрываемые детали строки с результатом «Успех»/«Дубликат»/«Ошибка», внешним ID и созданным HIS ID.
- Данные сертификата: SHA-256 fingerprint DER, issuer, serial number, subject, validity. Минимальный устойчивый идентификатор — issuer+serial либо SHA-256 fingerprint. Брать их из TLS, а не из полей HL7/запроса клиента.
- Успех попадает в транзакцию L3, отказы — после rollback. Не создавать ложный сертификатный аудит для TLS-handshake, на котором доверенная identity не установлена.
- Обновить типы/labels/filter/таблицу или детали аудита, время с секундами, человеческие подписи сервисного автора в ЭМК. Проверить отображение через существующую загрузку/обновление страницы аудита; SignalR в текущей HIS нет и добавлять его ради импорта не требуется.

**Приёмка:** из UI можно идентифицировать предъявленный cert и импортированного пациента; проверяется серверное происхождение metadata; API key/UAC/полный XML в аудит не попадают.

### L7. Запуск стенда и миграции без сброса лабораторной 3 — 3 SP

**Результат:** HIS для четвёртой лабы запускается одной понятной командой.

- Дополнить Makefile/скрипты: `make lab4-prepare`, `make lab4-run`, `make lab4-check` (реализованы в L7).
- Пробросить MLLP-порт и внешние пути сертификатов, объяснить hostname/SAN и отдельные HTTPS/MLLP параметры. Для desktop используется host-адрес, не Docker-only `his-api` без DNS на машине. Обновить allowlist окружения в `run-secure-development.py`, иначе новая секция настроек не попадёт в контейнер.
- Использовать клиентский выпуск T7 либо тестовые временные сертификаты, не заставляя L5 ждать T7. Приватный CA-ключ не монтировать в сервер/desktop runtime.
- Миграции применяются поверх лабораторной 3; при повторном запуске остаются admin, данные, LIS-сервисный аккаунт, ключи и история.

**Приёмка:** чистый тестовый профиль и upgrade существующей схемы; текущий `make lab3-run` и LIS работают; в инструкции нет обязательных ручных тяжёлых команд или секретов в CLI аргументах.

### L8. Сквозная приёмка и сценарий защиты HIS — 3 SP

**Результат:** доказано выполнение условия с настоящим desktop Тёмыча, а не только fake-клиентом.

- Вместе выполнить сценарии раздела 6; сохранить обезличенный отчёт без сертификатных private keys и токенов.
- Проверить роли всех трёх лабораторных, новую DB migration и регрессии FHIR/ЭМК/CSV/security. Запускать существующие проверки по затронутым областям; окончательный сквозной прогон требует обеих реализаций.
- Обновить `docs/system-guide-v1.md`: конфиги, как создать аккаунт/выдать клиентский cert, команды запуска, что показывать, как воспроизвести duplicate и отказ доступа.

**Приёмка:** заполненная матрица «требование → тест/экран → результат» и воспроизводимый прогон предоставленного XML по контрольным числам ниже.

## 5. Порядок независимой работы

| Этап | Лев | Тёмыч | Зависимость |
|---|---|---|---|
| Сразу | L1: wire fixtures/interfaces | T1: desktop skeleton/fake ports, ревью C4 | Короткое согласование wire; UI и skeleton не ждут его |
| Параллельно | L2, L3 | T2, T3, T7 | Каждая сторона использует предоставленный XML и fixtures, живое приложение партнёра заменяется fake |
| По fixtures | L4, L5 | T4, T5 | Каждая сторона тестируется против своего fake |
| Доведение | L6, L7 | T6, T8 автономные тесты/упаковка | Клиентские test-cert генерируются независимо |
| Вместе | L8 | T8 сквозная часть | Только этот этап требует обоих приложений и XML |

Нельзя обещать полную независимость последнего сквозного прогона. Отсутствие живого HIS не блокирует desktop; отсутствие desktop не блокирует server unit/TLS/PostgreSQL tests.

|---|---|---|

| Повторить полный XML, в том числе вариант с изменённым ФИО | Desktop + HIS | 50 duplicate, пациентов и записей диагнозов по-прежнему 50/100, старые данные сохранены |
| Открыть итоги и журнал desktop | Desktop UI | При первом прогоне 50/0/0 по успехам/дубликатам/ошибкам, после повторного 0/50/0, кнопки «Открыть журнал» и «Новый импорт» работают |

| Отозвать аккаунт / подставить LIS JWT | Desktop probe/import | Auth failure, медицинские данные не меняются |

Полный пакет может содержать частичный итог: успешные пациенты не откатываются из-за ошибки другого пациента. Атомарность — **на одного пациента**, как требует лабораторная.

## 7. Источники и решения, которые нельзя перепутать

- Первичный источник требований — предоставленный PDF «Лабораторная 4», 2 страницы. HL7 v2.8, MLLP/mTLS только для MLLP, UAC JWT, ADT A28, повторные DG1, MSA-3, атомарность, duplicate и неизвестные диагнозы — требования задания.
- Порт 2575, Fyne, имена классов, лимиты, один ADT на соединение, source `LAB4_XML`, названия Make-targets и оценки — выбранный проектный профиль, который можно уточнить в L1/T1.
- [HL7 v2.8, глава 2: control, UAC/MSA и типы данных](https://www.hl7.eu/HL7v2x/v28/std28/ch02.html), [глава 3: ADT](https://www.hl7.eu/HL7v2x/v28/std28/ch03.html), [глава 6: DG1](https://www.hl7.eu/HL7v2x/v28/std28/ch06.html), [глава 14: NMD/NCK](https://www.hl7.eu/HL7v2x/v28/std28/ch14.html), [ED](https://www.hl7.eu/HL7v2x/v28/std28/ch02a.html), [MLLP](https://hl7.eu/refactored/transport01mllp.html). В частности, использование MSA-3 для ID/ошибки — осознанное исключение задания, не обещание полной v2.8-conformance.
- Материалы от 14.11.2026 включают XML из раздела 3.1 и макеты HIS/desktop. Метрики файла подтверждены полным разбором. В макете итоги 46/4/0 иллюстрируют смешанный результат, приёмочные числа для полного уникального XML заданы в разделе 6.
- SourceTimeZone=Europe/Moscow, лимиты 3–32/3–256 и локальный DG1-6 `U` — предлагаемые решения после изучения XML. Файл содержит время без зоны и не содержит статуса диагноза.
- [OWASP: безопасный разбор XML](https://cheatsheetseries.owasp.org/cheatsheets/XML_External_Entity_Prevention_Cheat_Sheet.html).
