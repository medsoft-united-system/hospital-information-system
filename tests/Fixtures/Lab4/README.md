# Lab 4 C4-v1 contract fixtures

This portable package specifies the L1/T1 wire contract for the HIS and the separate Go desktop importer. It contains test data and expected results, not an HL7 decoder, an import service, a TLS listener or evidence that those components are implemented. The C4-v1 profile and the proposed `Europe/Moscow` source zone still require explicit review and consent from Тёмыч; that consent is **pending**. These fixtures do not mark L1/T1, the live integration or production readiness as complete.

The authoritative profile is [the Lev task card](../../../docs/lab4-lev-tasks-v1.md#3-общий-технический-контракт-c4-v1); [the teammate card](../../../docs/lab4-temych-tasks-v1.md) describes the independent Go implementation. Changes to this package and that profile must be reviewed together. Copy this entire directory into the Go project, record the reviewed HIS commit and compare `manifest.json` hashes; no shared runtime library or HIS database access is required. No real API keys, JWTs, refresh tokens, certificates or private keys are included.

## Source and normalized data

`patients.xml` is the exact, unmodified teacher file `Лабораторная 4 данные.xml` supplied for the lab and checked on 14 November 2026. Its 43,213 bytes are UTF-8; the root is `Patients`, the entry is `Patient`, and there is no namespace. SHA-256:

```text
4f822687e72db591d0263ad0c08449da68283327812452a5a020df530fbd0ca3
```

The complete parse yields 50 unique string patient IDs, 100 diagnosis occurrences and 25 distinct diagnosis codes. The distribution is 5 patients with zero diagnoses, 13 with one, 14 with two, 13 with three and 5 with four. `М` and `Ж` each occur 25 times. The file has no duplicate patient IDs or repeated diagnosis codes within one patient. Comments and `<diagnoses/>` are intentional. It is an instructor-supplied fixture; its identities are not asserted to be real people.

`normalized-patients.json` contains all 50 patients in XML order, using UTF-8 without a BOM. Its envelope is `{sourceSystem, sourceTimeZone, patients}`. Each patient has `sourceSystem`, `externalPatientId`, `firstName`, `lastName`, `middleName`, `sex`, `birthDate` and `diagnoses`; the repeated `sourceSystem` allows direct deserialization into a server input DTO. Sex is `Male` or `Female`, birth date is `yyyy-MM-dd`, and diagnoses contain `{code, title, codingSystem, diagnosedAt, diagnosisType}`. `codingSystem` is `I10` and `diagnosisType` is `U`. Every `diagnosedAt` is `yyyy-MM-ddTHH:mm:ss+03:00`, including all 100 source records. JSON keys and enumeration strings are case sensitive. Patient and diagnosis order is preserved; IDs and codes remain strings.

The XML contains local clinical times without any timezone. C4-v1 chooses the explicit `SourceTimeZone=Europe/Moscow`; this is a contract decision, not a timezone read from the source. Interpret every source value in this zone independently of the computer's local zone. All supplied dates have offset `+03:00`. For example, source `2023-05-14T10:20:00` becomes normalized `2023-05-14T10:20:00+03:00`, HL7 `20230514102000+0300` and instant `2023-05-14T07:20:00Z`. Reject nonexistent or ambiguous local times when other data/zones are used. DG1 transmits an offset, not the IANA zone name; retain the offset when storing clinical time.

Each of the 100 clinical diagnosis dates comes from its own source `diagnosed_at`. None comes from MSH, EVN, file metadata or import time. MSH-7, EVN-2 and NCK-1 are fixed at `20261113120000+0000` for deterministic byte examples. In a live sender they contain the current message/event time. HIS `AddedAtUtc` and history `OccurredAtUtc` are generated when the import runs; they are separate from the clinical `DiagnosedAt`. The manifest's source range describes clinical dates, not import dates. No fixture asserts a real commit time.

`normalized-synthetic-patients.json` uses the same schema for one deliberately synthetic patient. ID `000042` must keep its leading zeroes. The last name and diagnosis title contain every reserved delimiter (`|`, `^`, `~`, `\`, `&`). Two diagnosis occurrences share code `Z99.9` and title, with different clinical dates; preserve both occurrences and one definition per code. This case is absent from the teacher XML. The example UUIDs in ACKs are deterministic fake HIS results, never transformations of the external IDs.

## Exact wire profile

- Payloads are `.hl7` files encoded as UTF-8 without a BOM or LF. Every segment, including the last, ends in one byte `0D` (CR). Read these files as bytes when comparing them; text readers may normalize line endings. `.gitattributes` prevents Git newline conversion of payloads, frames and the exact XML source.
- Every normal `.mllp` file is exactly `0B` + the matching payload bytes + `1C 0D`. The final payload CR is retained, so the end normally contains `0D 1C 0D`. `.mllp` files are binary wire artifacts, not printable marker names. The single deliberate exception is `malformed-frame-payload.mllp`, which lacks the final CR of `1C 0D`; send EOF after these bytes and expect connection closure with safe diagnostics and no ACK.
- Use one request and its ACK per mTLS connection for v1. TCP is a stream: split/coalesced reads must still reconstruct the frame. The default port is 2575, maximum payload 1 MiB (1,048,576 bytes, excluding frame markers), maximum DG1 count 100. Proposed deadlines: TLS handshake 10 s, frame read 30 s, ACK/processing 30 s. These profile limits remain configurable, and are engineering choices rather than requirements quoted from the assignment. Oversize and NUL-containing frames are rejected; the provided malformed case is not a complete transport test suite.
- mTLS validates the server CA, validity and SAN/hostname, and the client CA, validity and Client Authentication EKU. JWT authorization is checked independently for every message. Client Subject CN is informational; it does not log in, choose a role or have to equal the account name. The fixture package provides neither TLS materials nor proof of working TLS.
- MSH-1/2 are `|` / `^~\&`; MSH-3/4 are `MEDSOFT_IMPORT` / `LAB4_XML`, MSH-5/6 are `HIS` / `MEDSOFT`. MSH-7 has an explicit offset, MSH-10 is a fresh message ID per send, MSH-11/12 are `P` / `2.8`, MSH-15/16 are empty for original acknowledgement mode, and MSH-18 is `UNICODE UTF-8`.
- Patient messages are `ADT^A28^ADT_A05` with segments `MSH`, `UAC`, `EVN`, `PID`, `PV1`, then zero or more `DG1`. UAC precedes EVN. EVN-2 equals MSH-7 for a new import. Keep `PV1||N` even when no visit exists. This is a constrained educational profile, not an implementation of all HL7 v2 structures.
- UAC-1 is `JWT^JSON Web Token^99MEDSOFT`. UAC-2 is the five-component ED value `MedSoftDesktop^application^jwt^Base64^<base64>`. Encode UTF-8 bytes of the raw access JWT, with no `Bearer ` prefix and no Base64 line wrapping. `application/jwt` is its MIME type; Base64 is not encryption. API keys and refresh tokens never enter HL7.
- All normal requests intentionally carry the non-secret string `lab4-fixture-access-token-not-valid`, Base64 encoded in UAC. It is not a valid JWT and a real validator must reject it. For codec/transaction cases a fake validator explicitly accepts this labelled fixture credential; the auth cases explicitly reject it. Live authorization tests must generate short-lived local tokens. `adt-invalid-uac-base64.hl7` deliberately contains invalid Base64. Logs and diagnostics redact UAC as `UAC: [скрыто]`, even when a fixture credential is used.
- PID-3 is `externalPatientId^^^LAB4_XML^PI`. It is a string, not a number or HIS UUID. PID-5 components are family name / first name / middle name (`PID-5.1.1`, `.2`, `.3`). PID-7 is `yyyyMMdd` with no time; PID-8 maps XML `М` to `M` and `Ж` to `F` (`U` is allowed for unknown values by the wider profile). An empty diagnoses list produces zero DG1 segments.
- DG1-1 is the ordinal `1..N`; DG1-3 is `code^title^I10`, where `I10` in the third component names the ICD-10 coding system. Code `I10` in the first component is a separate value and must not be confused with the system. DG1-5 is the clinical timestamp with explicit `±HHmm`; DG1-6 is exactly `U^Unspecified^99MEDSOFT`. The XML supplies no final/working status. Preserve complete codes/titles and every diagnosis occurrence. Existing code definitions keep their current title, with the source title retained in the imported snapshot.
- Escape data, not structural delimiters: `| → \F\`, `^ → \S\`, `~ → \R\`, `\ → \E\`, `& → \T\`. Each data character is escaped once. Decode escapes only after splitting structural fields/components; do not unescape a whole message before splitting. Cyrillic stays UTF-8. ACK error text follows the same rules.
- Probe messages are `NMD^N02^NMD_N02` with exactly `MSH`, `UAC`, `NCK`. NCK-1 contains the current time with offset and is informational: never set system clocks. The probe validates framing/auth and creates no patient; TCP connect or the separate authenticated HTTPS `/api/testConnection` does not replace it.

## ACK and client outcomes

An ACK has its own MSH-10, swaps sender/receiver, uses version 2.8 and copies the readable request trigger (`ACK^A28^ACK` or `ACK^N02^ACK`). MSA-2 must equal the request MSH-10 exactly. The use of MSA-3 for UUID/result text is an explicit legacy exception required by this lab; it is not the modern standard purpose of that field in v2.8.

| Meaning | MSA-1 | MSA-3 |
| --- | --- | --- |
| Patient and all diagnoses committed | AA | New valid HIS patient UUID |
| Same `(LAB4_XML, externalPatientId)` already imported | AE | `DUPLICATE: пациент уже импортирован` |
| Clinical validation failure with no partial writes | AE | `VALIDATION: безопасное описание` |
| Invalid/unauthorized access credential | AR | `AUTH: доступ запрещён` |
| Unsupported type/version/structure | AR | `PROTOCOL: безопасное описание` |
| Infrastructure failure after rollback | AE | `INTERNAL: импорт не выполнен` |
| Probe accepted, no patient written | AA | `CONNECTED` |

Auth ACKs include ERR-3 CWE code `207` (`207^Application internal error^HL70357`), ERR-4 severity `E` and generic ERR-7 `Доступ запрещён`. ERR is mandatory for auth failure; other errors may include it later by explicit profile revision. Responses never include a JWT, a decoded credential, SQL, exception details or key material. Authentication reasons such as expiry/signature/role are not disclosed.

Patient AA may be sent only after commit. Duplicate never updates the old patient, diagnoses or dictionary. A failed patient transaction rolls back the patient, external identity, EHR, all diagnosis occurrences, newly introduced definitions, history and success audit. Each patient is independent of the rest of the XML batch. A failed second diagnosis must not leave the first one behind. Safe refusal auditing is handled separately after rollback. These are expected service semantics, not implemented behavior supplied by fixtures.

The negative ACK fixtures deliberately mismatch MSA-2 or return AA without a UUID. Neither confirms success. Likewise a response lost after transmission may follow a committed import: the desktop shows «Исход неизвестен», and must not automatically retry the ADT. Only an explicit user retry is allowed; the external identity protects against duplicate insertion. A real re-send gets a fresh MSH-10, including when the patient is unchanged.

## Manifest and replay

`manifest.json` is language neutral. All artifact paths are relative to this directory. `normalizedPatient.index` is zero based in the referenced file's `patients` array. Each case gives `request`, `frame`, `requestMessageControlId`, an outcome expectation and, when applicable, `response`, `responseFrame` and `expectedAck`. `expectedAck` records decoded values, not escaped text. `normalizedPatient` links accepted/duplicate/internal/correlation inputs to exact typed data; invalid clinical inputs instead state their external ID. Fixture case UUIDs and control IDs are deterministic for comparison; live sends generate fresh values.

The expectation vocabulary is `accepted`, `duplicate`, `validation`, `auth_rejected`, `protocol_rejected`, `probe`, `invalid_ack_correlation`, plus the explicit fixture extensions `internal_error` and `invalid_ack_result`. Inspect `precondition` before replaying: outcome selection belongs to fake/test setup, not magic control-ID handling in production. Protocol-only cases check the codec; auth cases check safe rejection. A real endpoint will reject every included fake credential until a test substitutes a locally generated valid token. No fixture is permission to bypass real validation.

The package has 15 cases: three valid patient payloads, duplicate, two clinical validation failures, two auth failures, unsupported version, missing PID, rollback/internal error, successful probe, two invalid ACKs and one incomplete frame. The source-linked positive cases are XML patients `347821` (index 0, zero diagnoses) and `216734` (index 2, two diagnoses). The synthetic case covers all five escaped delimiters, leading zeros and one code at two clinical times. `acknowledgementExpected=false` means there is intentionally no response artifact. All other provided payload/frame pairs are exact.

`files` records SHA-256 and byte length for every package artifact except the manifest itself, which cannot include its own hash. Verify these after copying. For example, a Go fixture reader can use `os.ReadFile`, compare `sha256.Sum256` with the manifest, and decode JSON with a zero-based slice index. A replay fake can return the listed response bytes for a selected case without implementing the real database or JWT validation. The source hash, full 50/100/25 parse, all 100 clinical timestamps, escaping, frame bytes, ACK fields/correlation and auth redaction should be independently checked by both projects before marking C4-v1 agreed.
